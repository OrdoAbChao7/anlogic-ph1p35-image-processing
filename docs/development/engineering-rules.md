# 工程实现与交付规范

由项目 AGENTS.md 的工程条款整理而来（2026-10-20）；保留原条款编号便于追溯。RTL、接口、构建、硬件和发布任务按需读取对应章节。执行入口见 [Agent 工作流](agent-workflow.md)，目标见 [PROJECT_GOAL](../project/PROJECT_GOAL.md)，验收数值以 [验收矩阵](../verification/acceptance-matrix.md) 为准。本文件不记录当前通过状态。

## 8. 架构与接口原则

- 保留官方 MIPI、DDR、HDMI、PLL 和板级约束边界，算法优先作为明确像素流接口之间的独立层接入。
- 将采集、格式转换、帧缓存、算法、统计、OSD、时序生成和配置控制分层，禁止把整条链路堆进一个顶层文件。
- 模块只承担一个主要职责；接口必须说明位宽、采样周期、有效条件、延迟和复位行为。
- 数据通路与控制通路分离。模式或参数跨时钟域时使用可靠 CDC，并在帧边界更新会影响整帧一致性的参数。
- 优先采用逐像素流式处理。只有明确需要跨帧或异步速率匹配时才经过 DDR，避免无依据增加帧缓存和延迟。
- 顶层主要用于互连、时钟复位和板级端口；算法细节放在可独立仿真的模块中。
- 所有模式的输出尺寸、像素格式和同步时序应一致，使 HDMI 下游不依赖算法模式。


## 9. RTL 编码规范

- 新增应用 RTL 使用纯 Verilog；既有厂商 SystemVerilog/加密 IP 保持原样。测试平台方言由工具支持决定，不改变应用 RTL 的纯 Verilog 目标。
- 时序逻辑使用非阻塞赋值，组合逻辑使用阻塞赋值；组合过程提供完整默认值，禁止无意锁存。
- 禁止依赖 `initial`、仿真延时、不可综合系统任务或未声明位宽的隐式行为实现硬件功能。
- 所有算术明确有符号性、中间位宽、舍入、截断和饱和策略。Sobel、面积、坐标累加和尺寸换算尤其不得依赖默认位宽。
- Magic number 应提升为参数或具名常量，并说明单位和合法范围。
- valid、DE、帧行同步、坐标和像素数据经历同等流水线延迟；新增一级寄存器时同步审计所有伴随控制信号。
- 状态机必须有已知复位状态、默认转移和非法状态恢复策略。
- 异步输入先同步；多位数据跨域采用异步 FIFO、握手或稳定采样方案，禁止逐位双触发器同步。
- 复位释放应满足所在时钟域要求；禁止把无时序依据的组合复位传播到整条高速视频链路。
- 不随意修改厂商生成 IP 文件。配置变化应通过可追踪的 IP 配置或重生成流程完成。


## 11. 验证金字塔

验证按从快到慢的层次推进：

1. **静态检查**：语法、未连接端口、位宽、锁存、CDC、约束覆盖和未使用逻辑。
2. **模块仿真**：复位、最小/最大值、边界坐标、空白区、连续有效流、停顿和模式切换。
3. **参考模型比对**：测试图和真实采样图与软件黄金模型逐像素或按明确容差比较。
4. **子系统仿真**：验证多个模块串联后的总延迟、同步信号和帧边界。
5. **综合与实现**：查看资源、RAM/DSP 推断、关键告警、时序约束和最差路径。
6. **上板冒烟**：下载、锁相、摄像头启动、原图、处理模式、OSD、复位和模式切换。
7. **应用验收**：目标类别、空场、多目标、位置偏移、遮挡、光照变化和边界场景。
8. **发布验收**：冷启动、反复下载、长稳运行、演示脚本和备用恢复流程。

修复问题后先重跑最小相关层，再运行受影响的上层回归。测试失败必须保留首个根因证据，不得通过删除断言、放宽到无意义阈值或屏蔽告警制造通过。

没有硬件时可以完成到仿真和实现报告，但必须把“待上板”列为明确状态；屏幕截图不能代替构建日志、时序报告和测试记录。


## 12. 构建、约束与时序

- 项目应有唯一、文档化的构建入口，记录 TD 版本、器件型号、顶层、IP 版本和构建步骤。
- 源文件、约束和 IP 配置必须纳入交付；缓存、临时数据库和本机绝对路径不得成为构建依赖。
- 所有主时钟、生成时钟、输入输出延迟和合法异步关系都应有约束。禁止用虚假时钟、宽泛 false path 或 multicycle path 掩盖失败。
- 任何时序例外都要说明起点、终点、协议保证和验证方式。
- 报告 WNS/TNS、关键路径、时钟频率、逻辑、寄存器、BRAM、DSP 和主要 IP 占用；同时保留余量供最终集成。
- 关键告警逐项分类为已修复、已证明无害或阻塞。不得只汇报“0 error”而忽略关键 warning。


## 13. 硬件验收与测量

硬件结论应记录测试环境：板卡和模组版本、工具与 Bitstream 版本、分辨率、供电、显示器、镜头、距离、光照、目标物和操作步骤。

智能分拣 Demo 至少记录：

- 模型版本、输入尺寸、量化比例/零点、权重校验值和 NMS 参数。
- 正常样本、目标类别、多目标和无目标样本的定义。
- 每类样本的重复次数、定位误差、漏检/误检、计数错误和触发次数。
- 空场、遮挡、目标贴边、位置变化、光照变化和连续检测下的行为。
- 无法可靠检测时的 OSD 状态，以及 LED 和语音是否保持静默。

长稳测试应提前规定持续时间、通过标准和记录方式。测试期间关注花屏、撕裂、丢帧、锁相丢失、统计漂移、OSD 错位和死机；发生问题时记录时间、触发条件、可复现步骤和恢复方式。


## 14. 创新点判定

创新点必须同时满足：

1. 对题目二核心链路或智能分拣 Demo 有直接价值。
2. 在 FPGA 上真实运行，不是只存在于上位机或 PPT。
3. 有明确基线和单变量对照。
4. 至少改善资源、速度、延迟、精度、鲁棒性或可操作性中的一项。
5. 能用一张架构图、一组数据和一次现场演示解释清楚。

优先做少量可证明的亮点，不堆叠未经验证的算法。若新增功能损害基础视频稳定性、时序裕量或演示可重复性，先回退到稳定版本，再单独优化。


## 15. 文档与可追溯性

- 研究资料统一维护在 `docs/research/`，来源元数据维护在 `docs/research/sources.yaml`。
- 未确认硬件信息维护在 `docs/research/known-gaps.md`；关闭缺口时补充证据和结论，不直接删除历史问题。
- 架构说明应覆盖模块图、数据流、时钟复位树、接口表、流水线延迟和 DDR 使用方式。
- 实验记录应包含目标、版本、环境、步骤、预期、实际、证据、结论和后续动作。
- 设计决策要记录选择、备选方案、理由和影响，尤其是像素格式、ISP 插入点、缓存结构、量化参数、NMS 阈值、外设触发和模式切换。
- 文档、代码、报告、演示视频和 PPT 中的指标必须来自同一冻结版本。
- 路径优先使用仓库相对路径。不得提交账号、密钥、私有链接、本机敏感路径或无关大文件。


## 16. 变更纪律

- 每次只解决一个可验收问题，保持官方基线和最后一个稳定版本可恢复。
- 修改底层接口前先保存配置和报告，并说明修改理由、预期影响和回退方式。
- 不为追求“整洁”重写已验证厂商链路；重构必须服务于当前 Goal，并有等价回归证据。
- 用户已有改动默认保留。出现重叠修改时先辨认意图，不得直接覆盖、回滚或删除。
- 生成物与手写源文件分离。临时探针、转换文件和调试脚本在任务结束前删除，仍有复用价值的则正式命名并写明用途。
- 构建失败或硬件异常时，先复现和定位根因，再修改；一次只改变足以验证假设的最小变量。


## 17. 禁止事项

- 禁止编造器件参数、管脚、寄存器、IP 接口、测试结果、资源数据或时序数据。
- 禁止把其他 FPGA 平台能运行当作 PH1P35 可直接运行。
- 禁止跳过 Goal 1 的稳定链路，直接在未知视频接口上堆算法。
- 禁止用测试平台专用结构、整帧数组或不可综合代码声称实现实时硬件。
- 禁止用异步跨域、未约束路径或屏蔽告警换取表面上的编译成功。
- 禁止只保留成功截图而缺失失败记录、复现步骤和构建依据。
- 禁止为了增加创新点数量牺牲演示稳定性和交付完整性。
- 禁止在未验证时使用“完全兼容”“零误差”“无丢帧”“实时稳定”等绝对结论。


## 18. 每次任务的交付格式

面向用户先给影响与结论，再给改动、验证、风险和下一步；不存在的部分省略。完成实现类任务时至少说明：

- 修改了哪些文件和模块，以及为什么。
- 使用了哪些官方事实、工程事实和推断。
- 执行了哪些测试或构建，结果是什么。
- 哪些内容已在硬件上验证，哪些仍待上板。
- 新增或仍存在的资料缺口、时序风险和演示风险。
- 下一阶段的明确入口与退出条件。

只有在相关验证实际通过后，才可以声明任务完成。若受设备、资料、工具或用户决策阻塞，应交付当前可审查结果，并准确说明阻塞条件，不以猜测补全。


## 19. 最终发布清单

最终冻结版本至少包含：

- 可重建的 TD 工程、RTL、约束、IP 配置和构建说明。
- 已验证 Bitstream、版本标识和校验信息。
- 模块架构图、视频数据流图、时钟复位图和关键接口表。
- 仿真用例、软件参考模型、测试输入和结果摘要。
- 综合、资源、时序、帧率、延迟、功耗（若可得）和稳定性报告。
- 智能分拣 Demo 的模型版本、检测精度、计数稳定性、鲁棒性和失败边界数据。
- 目标样本、空场、多目标、复位、模式切换、LED/语音和长稳演示证据。
- README、接线图、上电下载步骤、现场演示脚本和故障恢复步骤。
- 演示视频、答辩 PPT、创新点对比表、常见问题和队员分工说明。
- 比赛要求逐项映射表，确保每项要求都能定位到实现与证据。

发布前最后一次验收必须从冻结包而非开发目录开始，按文档完整走通。只有冻结包能够独立复现并通过现场演示，作品才进入“可提交”状态。
