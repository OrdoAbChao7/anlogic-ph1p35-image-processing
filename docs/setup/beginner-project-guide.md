# SC520CS 图像处理竞赛项目：从现在到提交的操作手册

> 更新：2026-10-02。适用对象：第一次接触 FPGA、使用本机 `E:\Projects\FPGA` 的项目成员。项目范围、阶段门和证据规则以仓库根目录的 [AGENTS.md](../../AGENTS.md) 为准；比赛基本要求见[赛题摘录](../research/competition/topic2-requirements.md)。

## 先看结论：最终要做成什么

作品应让 SC520CS 的 RAW10 画面通过 MIPI、ISP 和 DDR2 进入 PH1P35，在 FPGA 内处理后经 HDMI 显示。现场屏幕能在原图、Sobel 边缘和卡通化三种模式间切换，OSD 显示安路 Logo、模式、帧计数、检测框、类别和总数；INT8 YOLO-tiny 完成常见目标检测，LED 和 WM8978 在检测事件下联动。最后用构建日志、时序报告、模型/RTL 比对、上板录像和外设记录证明它确实能运行。

这份手册按八个 Goal 排列。**每完成一关，先保存证据并核对“过关条件”，再进入下一关。** 软件仿真可以与到板准备并行；把算法接进视频主链路必须等 Goal 1 和 Goal 2 的关键事实确认后再做。遇到仍未知的硬件参数，查[资料缺口](../research/known-gaps.md)，不要猜引脚、FPC 方向、RAW 格式或时钟参数。

## 0. 第一次读这份手册：先认识五个词

- **工程**：TD 打开的一组 RTL、约束、IP 配置和顶层连接文件；不是一个孤立的 `.bit`。
- **RTL**：描述 FPGA 内数字电路的 Verilog/SystemVerilog 代码。
- **仿真**：在电脑上给模块输入测试像素并检查输出；它不等于真实摄像头测试。
- **构建**：TD 依次读取设计、综合、布局布线并生成 Bitstream；要看错误、告警和时序报告。
- **Bitstream / `.bit`**：下载到 FPGA 的配置文件。用 `PROGRAM_SRAM` 做初次试验通常需要每次重新上电后重新下载；不要把它当成已经写入 Flash 的启动程序。

每次开始一关，先读 [资料索引](../research/INDEX.md)、[来源表](../research/sources.yaml)、[资料缺口](../research/known-gaps.md) 和相应的 [Goal 阅读清单](../research/goal-reading/goal-1.md)。读不懂术语时，先照本手册执行，再回到资料页查含义。建议把每一次构建、下载和测试当成独立实验，按文末模板记下结果。

1. 断电清点并拍照；根据**到手板卡和 SC520 模组的对应资料**确认供电、摄像头 FPC、HDMI、板载下载器的连接方式。确认不了 FPC 方向时先停在这里，提供正反面清晰照片及资料页，再核对；不要试插。
2. 接好显示器与数据线。按到手板卡手册连接供电和 USB 下载口，上电后检查电源指示、电脑设备管理器是否识别下载接口。若驱动缺失，先查官方资料包 `1_安路工具和软件/（必看）PH1P35烧写程序的使用方法.pdf`，其中给出 `UsbDriverTool.exe` 的位置和本板 USB 接口的识别方式；**仅操作确认为该开发板的 USB 接口**。TD 内已有 `hwserver.exe`，先试现有版本，别直接覆盖它。
3. 打开原图工程：`pwsh -File .\scripts\open-td.ps1`。在 TD 工具栏点击 `BitWriter`。按官方烧写指南选择本地 `AL-LINK-FT(Local Host)` 服务；若界面要求端口，指南示例为 `5555`。点击 `Refresh`，在设备出现后选中并确认目标器件。若始终没有设备，先回到供电、USB 线、设备管理器和驱动检查，不选一个名称相似的其他设备。
4. 首次试验选择 `PROGRAM_SRAM`，点击 `Add` 选择上述原图 `.bit`，再次核对完整路径和哈希，然后点击 `Run`。界面文字若与资料不同，以本机 TD 窗口和当前板卡说明为准。

## 3. Goal 2：画清楚数据、时钟和接口

**目标：** 任意一颗像素从哪里来、在哪个时钟域、以什么格式进入算法、怎样去 HDMI，都能在工程里定位。先读 [Goal 2 清单](../research/goal-reading/goal-2.md) 和[现有接口表](../../preboard/02-interface-contract.md)。

1. 在原图工程的 TD 文件树中找到顶层 `design_top_wrapper.v`，记录顶层实例之间的连接。按“摄像头配置 → MIPI 接收 → 格式转换/ISP → DDR 写入 → DDR 读出 → HDMI 输出”的顺序追踪模块；遇到厂商 IP 时记录实例名、配置文件和文档，不直接改生成文件。
2. 对每段连接填写[接口表](../../preboard/02-interface-contract.md)：时钟与频率、复位、每拍像素数、位宽和颜色顺序、帧/行/像素有效信号、背压、缓存、固定延迟、证据路径。资料没写的字段标 `unknown`，不要从模块名猜。
3. 在工程与报告中找到时钟约束和 PLL 输出；检查摄像头 MCLK、MIPI、DDR、HDMI 的时钟来源、跨时钟域边界与复位释放。把时序报告的 WNS/TNS、未约束路径和普通告警逐项记录；宽泛的 false path 不能用来掩盖真实错误。
4. 确认算法插入点前的像素究竟是 RAW/Bayer、灰度还是 RGB，确认 `DE`/`valid`、坐标与像素是否同拍。为这个插入点写一条简单的设计决策：为何选它、前后接口是什么、预计增加几拍延迟、对 DDR 和 HDMI 有何影响。
5. 用一张模块图、一张时钟/复位图和一张接口表让另一位成员能从 MIPI 追到 HDMI。如果任何关键字段仍未知，先以小范围仿真、报告或板上探针补证据。

**过关条件：** 关键像素流接口和时钟域有可定位的工程/报告证据，算法插入点已冻结，延迟和同步语义可解释。不得在 RAW/Bayer 尚未确认时把其当作 RGB 接入灰度模块。

## 4. Goal 3：灰度、二值化和模式切换

**目标：** 原图、灰度、二值化切换后，画面尺寸与同步仍一致。先读 [Goal 3 清单](../research/goal-reading/goal-3.md) 和[算法契约](../../preboard/03-algorithm-contract.md)。

1. 从 Goal 2 的插入点取一张真实像素格式说明。如果输入是 RGB，明确 R/G/B 位宽与通道顺序，选定整数灰度系数、舍入和饱和规则；如果是 RAW/Bayer，先确认既有 ISP/格式转换，不把 RAW 直接当灰度或 RGB。
2. 在软件参考模型里落实同一套公式与阈值语义。用全黑、全白、阈值附近像素和真实采样图验证。当前参考模型已有 8 位灰度的二值化、Sobel 和 BBox 候选规则，但尚无 RGB 灰度与真实视频格式结论。
3. 新建独立 RTL 模块，端口清楚传递像素、`valid`/`DE`、行帧同步及必要坐标；模式和阈值在帧边界锁存。每增加一级流水线寄存器，同时延迟数据和所有控制信号。
4. 先仿真单模块：复位、第一/最后像素、空白区、阈值 `0` 与 `255`、连续有效像素、模式切换。把输出与软件模型逐像素比对，并写明允许误差。再仿真与前后级连接的帧首、行首和总延迟。
5. 完成综合、布局布线，查看资源、关键告警和时序；对照 Goal 1 的原图链路上板。按原图 → 灰度 → 二值化切换，录像并确认 OSD/HDMI 没有错行、闪烁或色序错误。每次只接入一个新增能力。

**过关条件：** 模型、RTL 仿真和板上模式画面一致；模式切换不破坏视频同步；构建时序和资源可审计。纯软件输出不算这一关的硬件完成。

## 5. Goal 4：用流式电路做 Sobel 边缘

**目标：** 在实时像素流上形成 `3×3` 窗口，计算 Sobel 边缘并输出。先读 [Goal 4 清单](../research/goal-reading/goal-4.md)。

1. 按当前有效图像宽度设计两条可综合 Line Buffer 和 `3×3` 移动窗口；确定在新一帧、每行开头和末尾怎样清零或输出边界。不能用只适合仿真的整帧数组冒充实时硬件。
2. 先用小图仿真窗口本身，给每个像素一个可辨认编号，逐拍检查窗口对应的图像坐标、首两行、末两行和帧切换。若输入可能停顿，定义并测试 `valid` 为空时窗口怎样保持。
3. 冻结 `Gx`、`Gy`、绝对值、相加、饱和到 8 位和边缘阈值。当前候选软件规则是 `min(255, |Gx|+|Gy|)`，外圈为 0；变更时同步改软件模型、测试和 RTL。
4. 逐像素比对全黑、阶跃、棋盘格、贴边目标和真实样图。接入原图链路后跑综合与布局布线，看 Line Buffer 是否推断为合理 RAM、WNS/TNS、关键路径、资源余量及控制信号总延迟。
5. 上板切换到 Sobel，移动零件与相机视野中的边界，观察连续视频并录像。记录输入/输出模式和具体构建版本。

**过关条件：** 窗口时序、边界和参考模型一致；电路可综合并满足时序；HDMI 实时演示可重复。

## 6. Goal 5：统计目标面积和外接框

**目标：** 从二值结果得到目标面积、BBox、宽度、高度及必要的位置，并只在帧边界更新对外结果。先读 [Goal 5 清单](../research/goal-reading/goal-5.md)。

1. 明确前景颜色、有效 ROI、噪声策略和多目标策略。最小实现可以把所有前景像素合为一个 BBox，但应在画面和说明里写清限制。
2. 对当前帧用足够位宽的寄存器累计面积、最小/最大 `x/y`；帧开始清零，只有有效像素且位于 ROI 内才更新。帧结束时把本帧结果锁存到显示寄存器，避免画面中途显示半帧数据。
3. 空目标输出 `valid=0` 或等价无效状态；宽高按端点包含的定义计算：`xmax-xmin+1`、`ymax-ymin+1`。面积不能因计数器溢出而回零；位宽须根据已确认的最大有效区推导。
4. 在仿真中覆盖空场景、单个像素、贴边物体、两个独立物体、噪声、连续帧移动和复位。与软件参考模型对比 BBox 与面积；模式/阈值变化时确认帧内参数一致。
5. 上板显示 BBox 和数值，用固定零件多次摆放，记录跳动范围。若结果抖动，先检查照明、背景、ROI 和分割阈值，再考虑滤波或帧间稳定策略。

**过关条件：** 所有边界场景有仿真证据，帧间结果不会混帧；固定物体实测的重复性数据可记录，多目标限制写清楚。

## 7. Goal 6：完成智能分拣显示与外设 Demo

**目标：** 一个非开发者按说明放入目标样本，屏幕能稳定显示检测框、类别和数量，并触发 LED/语音。先读 [Goal 6 清单](../research/goal-reading/goal-6.md)。

1. **固定工位。** 固定相机高度/角度、镜头焦距、目标放置区域、照明和背景，记录距离、光源和样本编号。
2. **冻结模型规则。** 记录模型版本、输入尺寸、INT8 量化比例/零点、权重校验、类别表和 NMS 阈值，不在验收中临时改参数。
3. **形成检测链路。** 逐项验证卷积、池化、BRAM 特征图、候选框解码和 NMS；空场、遮挡、贴边和光照变化应有明确的无效或低置信行为。
4. **叠加 OSD。** 在 HDMI 上显示安路 Logo、工作模式、帧计数、BBox、类别和目标总数。结果在帧边界更新，避免静止目标闪烁。
5. **联动外设并记录。** 检查按键去抖、LED 触发、ROM 语音读取和 WM8978 DAC 输出；记录漏检、误检、计数错误、重复触发和恢复步骤。[到板记录表](../../preboard/04-bringup-and-demo.md) 可直接填写。

**过关条件：** 目标类别和数量可重复检测，OSD、LED、语音与事件同步，检测误差与适用边界有数据，现场操作步骤可复现。

## 8. Goal 7：在稳定版本上做可证明的优化

**目标：** 留下两到三个对核心链路有价值、可量化的创新点。先读 [Goal 7 清单](../research/goal-reading/goal-7.md)。

1. 冻结一份 Goal 6 稳定基线：保存源码 commit、Bitstream 哈希、资源、WNS/TNS、帧率、延迟、精度和演示视频。
2. 一次只改一个变量。优先考虑流式流水线降低延迟、BRAM 复用和 INT8 位宽优化、卡通化资源优化、NMS/检测稳定化。对尚无平台证据的其他协同结构不当作必选目标。
3. 用同一输入、同一工位、同一构建条件对比优化前后：逻辑/寄存器/RAM/DSP、最差时序、吞吐/帧率、延迟、定位误差、漏检/误检和计数错误。记录收益，也记录代价。
4. 把结果做成一张架构图、一张对比表和一段真实硬件演示。若新功能损害视频稳定性或时序，回到保存的稳定版本，再单独定位。

**过关条件：** 每个宣称的创新点都有运行在 FPGA 上的实现、单变量基线、量化收益和适用范围。没有测量就只称“尝试”，不称“优化成功”。

## 9. Goal 8：冻结、打包、长稳和答辩

**目标：** 别人拿到交付包能重建并演示，不依赖开发电脑上的隐含文件。先读 [Goal 8 清单](../research/goal-reading/goal-8.md) 和[赛题要求](../research/competition/topic2-requirements.md)。

1. **冻结版本。** 选定最终 commit、TD 版本、板卡/模组版本和 Bitstream 哈希。冻结后只修复阻塞发布的问题；任何修复都重新编号并重跑受影响验收。
2. **整理可重建工程。** 核对 RTL、约束、IP 配置、脚本和版本说明是否齐全。当前 `.tools/td/` 下的官方工程和生成物被 Git 忽略，因此必须完成许可与来源审计，整理可交付源文件并去掉本机绝对路径，再从干净目录做一次构建。不能把当前 GitHub 仓库说成已经可独立重建。
3. **从冻结包重测。** 按说明构建、下载、冷启动、热复位、模式切换、目标/多目标/空场测试，并检查 LED 和语音。预先确定长稳测试持续时间、通过标准与记录方式；记录花屏、撕裂、丢帧、锁相、OSD 错位和恢复方法。
4. **汇总证据。** 保存最终 Bitstream 与校验值、完整日志、资源和时序报告、视频格式和帧率依据、端到端延迟的测量或可审计计算、模型/权重校验、检测误差、外设记录、演示视频、工位照片和异常场景记录。报告中的每个数都应指向同一冻结版本。
5. **准备现场材料。** 写 README、接线与上电下载步骤、演示脚本、故障恢复步骤、架构图、时钟复位图、PPT、创新点对比表、常见问题、队员分工和比赛条款到证据的逐项映射。让另一位成员只按文档实际操作一次，记录卡住的步骤并修正。
6. **最后验收。** 从最终交付包而不是开发目录完整复现；检查交付内容与 PPT、视频、现场 Bitstream 一致。发现缺项就回到对应 Goal 修复，不靠口头解释补齐。

**过关条件：** 冻结包可独立重建、下载和现场演示；长稳及异常场景达到预先写好的标准；所有赛题基本要求和项目宣称都有可定位证据。到此才称“可提交”。

## 10. 出问题时从哪里查

| 现象 | 先做的检查 | 需要保存的证据 |
| --- | --- | --- |
| TD 打不开 | 在仓库根目录重跑 `open-td.ps1`；看弹窗/终端原文和 [TD 记录](tangdynasty.md) | 命令、错误截图、TD 版本 |
| 找不到 `.bit` | 确认打开的是 SC520 原图还是修复副本；检查构建流程是否走到 `Generate Bitstream` | `run.log`、工程路径、文件列表 |
| BitWriter 找不到板卡 | 检查供电、USB 线/接口、设备管理器及官方驱动；在 TD 刷新下载器 | 设备管理器、BitWriter 截图、板卡标识 |
| 下载成功但黑屏 | 先看显示器输入源、HDMI 线与显示模式，再分段核对摄像头供电/配置、MCLK、MIPI 接收和 HDMI 输出 | 下载日志、画面视频、模块状态/探针 |
| 有图但花屏、错色或卡顿 | 记录触发条件；检查像素格式、同步、DDR 缓冲、时钟和时序报告 | 视频、`route.qor`、相关波形 |
| 新算法后画面错位 | 回到原图基线，核对像素数据和 `valid`/`DE`/帧行同步的流水线延迟 | 前后波形、仿真差异、commit |
| 检测不稳定 | 固定工位，核对光照、输入缩放、量化参数、NMS 和帧间结果锁存 | 同一目标的重复检测表 |

先保留**第一次失败**的日志与画面，再改一个最小变量复测。不要删断言、屏蔽关键告警或同时改传感器、PLL、DDR 和算法，让问题无法归因。剩余未知项继续登记到[资料缺口](../research/known-gaps.md)。

## 12. 从今天开始按什么顺序做

**板卡还没到：** 先完成第 1 节电脑和备料清单，读 Goal 1 与 Goal 2 资料；运行参考模型并理解一张测试图的二值化与 Sobel 输出。可以提前准备灰度/Sobel 的软件向量和仿真设计，但保留与未知像素格式有关的决策。

**板卡到了：** 先核对型号、模组与 FPC，再完成 Goal 1 原图上板。第一次成功出现移动画面时立刻保存视频、下载日志和 Bitstream 哈希；随后做复位与重新上电。只有 Goal 1 的证据齐全，才继续 Goal 2 的接口冻结和算法接入。

**每完成一关：** 更新对应研究资料、实验记录与未关闭缺口，保存可恢复版本，再做下一关。任何阶段如果被板卡、资料或工具阻塞，明确写下“缺什么证据、谁能提供、拿到后第一步做什么”；软件构建和仿真仍可继续，但不得把未上板的功能标为完成。
